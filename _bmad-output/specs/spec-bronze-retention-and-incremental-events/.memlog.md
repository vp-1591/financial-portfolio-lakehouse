goal: Preserve broker data while removing unnecessary raw duplicates and stale freshness semantics
updated: 2026-08-21T15:28

- (direction) The user selected one broker-scoped bronze table with broker-specific retention and deduplication instead of a separate observability table.
- (decision) Raw retention keeps the latest XTB report per account, the latest Trading 212 response per endpoint, and all IBKR event coverage needed to avoid Flex query-window loss.
- (decision) Normalized IBKR events must be dedup-append by event_id rather than overwrite so events missing from a later Flex response remain available.
- (constraint) XTB account_id is not a RAW_SCHEMA field; current code derives it from source_file during silver transformation, so any raw retention key must preserve that boundary or add an explicit ingestion identity design.
- (decision) Delta deleted-file retention defaults to one week and Delta log retention defaults to 30 days; VACUUM is not automatic, so defaults alone do not implement raw retention.
- (capability) Broker-specific bronze retention. intent: Keep only the raw payload history required by each broker's data semantics while retaining one raw table per broker. success: XTB retains the latest report per account, Trading 212 retains the latest response per endpoint, and IBKR retains sufficient event payloads to cover normalized event history.
- (capability) Incremental normalized events. intent: Preserve existing normalized events while adding or updating events from new broker fetches instead of replacing the entire events table. success: IBKR events absent from the latest Flex response remain in normalized storage, repeated event_id values resolve to the latest version, and no event is lost because the query window moved.
- (capability) Fresh fetch timestamps. intent: Make normalized freshness reflect the current successful fetch even when the raw payload is deduplicated. success: identical repeated fetches do not produce stale freshness warnings solely because their payload hash already exists.
- (constraint) Trading 212 and XTB assumptions are explicit: Trading 212 responses are complete for their endpoints; XTB account identity is the logical retention boundary; broker corrections and response truncation are out of scope unless tests or source contracts contradict these assumptions.
- (constraint) A Delta table's default seven-day deleted-file retention applies only when VACUUM removes logically deleted files; append-only writes do not delete old rows, and the default Delta log retention is 30 days.
- (question) How will the implementation derive or persist an XTB account retention key without adding account_id to RAW_SCHEMA, which ADR 0047 intentionally keeps out of bronze?
- (question) Does issue #155 require retaining the existing Trading 212 handoff optimization, replacing it with incremental event writes, or adding per-layer filtered reads for IBKR/XTB? Confirm the issue's exact acceptance criteria before implementation.
- (question) Should bronze retention be implemented as physical row deletion/compaction, or as write-time admission of only the broker-specific latest rows followed by a scheduled VACUUM policy?
- (assumption) Issue #155 is related because it extends the current handoff design toward per-layer handoff, filtered reads, and bounded dedup scans; it can share this PR only if its acceptance criteria remain within the retention and incremental-events contract.
- (note) Issue #157 is addressed by removing the false stale-fetched_at path: normalized event history is append-preserved while current fetch metadata or current-fetch transformation supplies freshness.
