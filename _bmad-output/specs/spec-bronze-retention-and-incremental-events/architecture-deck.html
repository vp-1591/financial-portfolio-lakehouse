Bounded Bronze, Incremental Events

The raw layer becomes a bounded cache — one row per broker retention key, enforced at write time by a Delta MERGE — and silver events become the durable history, merged by event identity and never deleted. Freshness is a property of the run, not the stored bytes.

One run, end to end

fetch bronze — merge-on-key retention silver — durable gold quality — run-aware freshness

AD-1 Retention = write-time merge-on-key

The fetch itself is a Delta MERGE on the retention key. There is no accumulated table to scan for dedup, and no separate retention sweep — the retained set is the table.

AD-3 VACUUM per run, 7-day default

Tombstones created by the merge are drained once per run with the Delta 7-day default. No low-retention override — logical, physical, and log retention stay distinct.

The eight decisions

Click a card to expand. Every decision carries Binds / Prevents / Rule.

AD-1 Retention is write-time merge-on-key

Binds: CAP-1, CAP-4, every fetch_*, raw/ingest.py, the removed dedup accumulation scan

Prevents: “latest per key” computed two places; the accumulated read-back (the read/dedup work this epic kills, issue #154 memory driver); out-of-policy rows surviving forever.

Rule: raw write = DeltaTable.merge of the batch keyed on XTB account_id, T212/IBKR source. Matched rows replaced, unmatched inserted, unseen keys untouched. Batch pre-deduped on (source, payload_hash). Cross-run dedup_raw scan deleted.

AD-2 RAW_SCHEMA + nullable account_id, − source_file

Binds: CAP-1 · RAW_SCHEMA · XTB fetch + transform · migration

Prevents: identity landing in two columns; null-account_id collapsing unrelated brokers into one merge key.

Rule: schema = fetched_at, broker, source, payload, payload_hash, account_id (nullable). XTB populates account_id from the report filename; IBKR/T212 store NULL and never merge on it; transform parses payload when null, ties on fetched_at+payload_hash. Supersedes ADR 0047's account_id clause (recorded, not silent).

AD-3 VACUUM per run, 7-day default

Binds: CAP-4 · every environment endpoint (docker/staging/prod)

Prevents: relying on the 7-day default as if it were retention; and the inverse — an aggressive low-retention vacuum that risks live data.

Rule: vacuum(dry_run=False) with defaults (retention_hours omitted, enforce_retention_duration True) at end of run — dry_run defaults to True and would delete nothing. Per-connector task vacuums its own raw/{broker} (XTB's file-arrival task vacuums raw/xtb); silver events never vacuumed. Logical, physical and log retention stay three distinct mechanisms.

AD-4 Events are append-preserving MERGEs

Binds: CAP-2 · normalize.py events write · dedup_events

Prevents: today's mode="overwrite" (normalize.py:218) wiping events absent from the latest response — the Flex-window loss CAP-2 kills; and delete-then-insert “simplifications”.

Rule: events = DeltaTable.merge on the per-broker event identity (subset containing event_id, ADR 0105). whenMatchedUpdate only when newer fetched_at; whenNotMatchedInsert. Nothing ever deleted by a merge. Idempotent; moving the Flex window cannot remove events.

AD-5 Freshness is run-aware

Binds: CAP-3 · quality.py freshness · run.py

Prevents: issue #157 — a byte-identical re-fetch warns stale because stored max(fetched_at) is the first payload's timestamp.

Rule: the run passes per-broker last-successful-fetch times into the freshness pass; a table whose broker was fetched within the window passes even if nothing changed. Standalone DQ falls back to table max(fetched_at). No new table — the run is the marker.

AD-6 One bronze read feeds both outputs

Binds: CAP-5 · transform_connector · both transforms

Prevents: each downstream table independently re-reading and re-parsing the same encrypted payload (doubled reads, divergent decodes).

Rule: transform_connector reads raw/{broker} once post-merge; the same decoded result routes to snapshot and events. No per-table raw re-reads. Removing the T212 handoff (AD-8) makes this the only path.

AD-7 Schema migration is the deploy gate

Binds: CAP-1 · migrations · deploy per environment

Prevents: merge-on-account_id code deployed against pre-schema tables (NULL-keyed legacy rows → re-insert every run); dropping source_file before the backfill.

Rule: migration rewrites raw/{broker} to the new schema, backfills XTB account_id from source_file, then drops it. Idempotent, --dry-run, per-environment pre-deploy with connectors idle. Events tables need no migration (write-only change).

AD-8 T212 handoff removed — measured, reversible

Binds: CAP-5 · trading212 connector · the ADR 0116 baseline

Prevents: two implementers disagreeing on keep-vs-delete, and shipping without an empirical gate.

Rule: remove the handoff; measure memory peak + runtime against the baseline; restore on material regression. Either way, one shared bronze read (AD-6) stays.

Keys absent from the current fetch are never deleted. A fetch merges only the keys it saw; a broker that stops reporting keeps its last row. The “replace with the current response” trap is what the events merge avoids and raw's merge-on-key inherits.

Deploy ordering & operations

Migrate before deploy, per environment, connectors idle — the ADR 0112 A1 convention.

StepWhat
1Run pipeline/migrations/migrate_raw_account_id.py --mode <env> --dry-run, then for real — backfills XTB account_id from source_file, drops source_file.
2Deploy the new code (merge writes, run-aware freshness). Events tables need no migration — the CAP-2 change swaps the write mechanism, not the schema.
3VACUUM runs at the end of every broker run with the 7-day default. Expected: pipeline.run query "SELECT broker, COUNT(*) ... GROUP BY broker" stays flat.
4Measure the T212 run without the handoff (memory peak + runtime) against the ADR 0116 baseline; restore on material regression.

How freshness stops false-stale (issue #157)

Old: freshness = max(fetched_at) of stored rows → an identical re-fetch stores nothing new → warns stale even though the run succeeded.
New: the run passes its own last-successful-fetch timestamps into the quality pass → a broker just contacted within the window passes regardless of payload change; standalone DQ falls back to the table scan.
